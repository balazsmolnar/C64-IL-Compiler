# C64Presentation: modern deck brief

Shared ground rules for everyone (people and agents) rebuilding the
presentation. Read this, `CLAUDE.md` and `Catacombs/TECH.md` (graphics API,
asset tools, memory map) before touching anything.

## The goal

The deck is a talk about this project: running C# on a Commodore 64 through
an IL -> 6502 compiler. It runs on a real/emulated C64 and must look like a
**modern PowerPoint / Keynote deck**, within the C64's limits: a consistent
theme, clean typography, real pictures and diagrams, charts, smooth
transitions and builds. Someone seeing a screenshot should think "a designed
slide deck", not "a BASIC listing". The C64 identity can show (it is the
point of the talk), but as deliberate style, not as a default-font accident.

Benchmarks for the bar: a current PowerPoint "Designer" theme, Apple Keynote
default themes, a good conference talk deck. On the C64 side: the best
modern demo-scene slideshows and title screens.

## Design rules

- One theme across all slides: a master layout with a title area, a body
  area and a footer (deck title / slide number / progress), fixed margins
  and a grid. Every slide uses it unless it is deliberately a full-bleed
  section or title slide.
- Typography: a designed font, not the ROM font. Hierarchy (title, body,
  caption) through size, weight, case and colour. Text never touches the
  border or another element; nothing overlaps by accident (today the slide
  counter overwrites the memory slide's heap box).
- Colour: a small deliberate palette (background, primary text, secondary
  text, one or two accents) chosen from the 16 C64 colours, used the same
  way on every slide. Good contrast.
- Visuals: real images (logos, diagrams, screenshots, charts) where
  PowerPoint would have them. Diagrams beat bullet lists.
- Motion: transitions between slides and builds within a slide (bullets
  appearing, a diagram drawing itself), quick and tasteful; no flicker, no
  visible redraw garbage.
- Hi-res bitmap (320x200) is probably the right base for crisp text and
  lines; multicolour images are fine for pictures. The engine owner
  decides and documents it.

## Content (keep, update, extend)

The talk explains: what the project is, how the pipeline works (C# -> IL ->
compiler passes -> 64tass -> .prg), the language features and their
limits, memory layout, the garbage collector, **the compiler optimizations
(new: shared exit tails, static frames, top of stack in A, logic-op
fusion, table-driven initializers, division by constant... with measured
before/after numbers from git history)**, Catacombs as the showcase (a full
AAA-style game written in C#), live demos, and a close. Facts and numbers
must be true: take them from the code, `git log` and commit messages, and
`Catacombs/TECH.md`; never invent a figure.

Navigation stays: SPACE / joystick fire = next, B = back.

## The code is part of the demo

The deck's own source is shown off as "this deck is C# too", so it must
read like modern, idiomatic C#: file-scoped namespaces, object and
collection initializers / collection expressions (`[a, b]`), target-typed
`new()`, `init` properties, expression-bodied members, switch expressions
and patterns, string interpolation, raw string literals, primary
constructors, `static` and `readonly` where they fit, small focused
classes, no C-in-C# (magic numbers, manual index juggling, copy-pasted
blocks). Slides stay real C# code -- never a data/script format -- written
as declarative initializers where possible, with custom code only for
genuinely animated slides. When a modern construct is not supported by the
compiler yet, prefer adding generic compiler support (with tests, pay only
for what you use) over writing old-style C#; if that is too big, note it.

## Technical rules

- Compiler / C64Lib / asm runtime changes are welcome but must be GENERIC
  (useful to any C64Lib program) and follow `CLAUDE.md`: unsupported C# is a
  coded diagnostic, and "pay only for what you use" (`Hunchback/measure.bat`
  segment sizes must stay identical when Hunchback doesn't use the feature).
  Run the affected test suites.
- Slide content and layout live in C#; hand-written asm belongs in the
  generic runtime (`asm/`), not in the presentation.
- uint/int are 8-bit, ulong is 16-bit. The locals stack is 256 bytes: keep
  call chains shallow. The compiler now has static frames (see CLAUDE.md).
- Assets are generated by checked-in scripts (Python 3 + Pillow) under
  `C64Presentation/art/`, converted with `tools/c64img.py` /
  `tools/c64spr.py`; never paste opaque byte blobs without their source.
- Memory is finite: the program plus all images must fit. Budgets below are
  hard; watch the segment map the build prints.
- Anything that writes past screen memory corrupts the runtime's object
  tables at $0800 (that bug just broke the deck once). Stay in bounds.

## Looking at the deck

Never synthesize keypresses into VICE. Scene builds instead:

    & "<root>\tools\presentation-shot.ps1" -Root "<root>" -Slide 3 -OutPrefix "<root>\.debug-tmp\s3_" -Shots 3 -IntervalMs 600

(write `<root>` out as the literal absolute path every time: no `$wt`/`$root`
variables, no `cd <dir> &&`, no `Join-Path` -- any path computed at run time
makes the sandbox stop and ask the user for permission; see CLAUDE.md)

`-Slide N` boots into slide N (0-based); `-Scene HOLD` (the default) keeps
it up, `-Scene AUTO` makes the deck advance by itself, for checking
transitions and the whole run. All "advance" input must go through
`Helper/KeyBoard.cs` (`AdvancePressed` / `WaitForKeys`) so these scenes keep
working. Several shots a few hundred ms apart show animation. Several of
these can run at once; never call `vice-launch.ps1`/`vice-close.ps1`
without `-KeepOthers`/`-ProcessId`. The first frames after launch can
contain a stray keypress from VICE's own autostart typing.

## Who owns what (parallel work, merged afterwards)

Each part is built on its own branch and merged later, so stay inside your
own files. Edits to anyone else's file must be the smallest possible call
into your own code.

| Part | Owns | Budget |
|---|---|---|
| Engine and theme | `Presenter.cs`, `Slides/Slide.cs`, `Slides/SimpleSlide.cs`, `SlideElements/*`, `Animations/*`, `Helper/*`, the font, the master layout, transitions; keeps every existing slide running on the new engine | 8 KB code + font |
| Story | `DECK.md`: the storyboard -- every slide's title, text, visual, build order, speaker point, and the facts/numbers with their source | no code |
| Art | `art/**` (scripts and generated assets), `Assets.cs` (the `[RawImage]`/`[RawSprites]` declarations) | 18 KB of compressed images |
| Slides (later phase) | `Slides/*Slide.cs` content and `Program.cs`'s slide list, built from `DECK.md` on the engine with the art | what is left |
