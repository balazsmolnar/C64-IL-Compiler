# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An experimental compiler that takes compiled .NET IL (from a normal C# project targeting `C64Lib`) and translates it into 6502 assembly (64tass syntax) that runs on a real/emulated Commodore 64. The pipeline is: C# source → `dotnet build` produces a .dll → `Compiler.exe <dll> <output-folder>` reads the IL via `System.Reflection`/`System.Reflection.Metadata` and emits `.asm` files → `64tass` assembles those into a `.prg` → run in the VICE emulator (`x64sc.exe`).

`C64Lib` is the API surface a C# "C64 program" is written against (e.g. `C64.SetChar`, `C64.Sprites`, `Sound`, `Joystick`). Its methods are empty/no-op stubs in C# — they exist only to give the compiler type/signature info; the actual behavior comes from hand-written 6502 helper macros in `asm/helper/*.asm` that the compiler's emitted code calls into.

## Solution structure

- `Compiler/` — the IL → 6502 asm compiler (`Compiler.exe`). Runs as an ordered list of `ICompilerPass`/`ICompilerTypePass`/`ICompilerMethodPass` implementations (see `Compiler/Program.cs`), each pass transforming/annotating a `CompilerContext` → `CompilerTypeContext` → `CompilerMethodContext`. Passes fall into three groups:
  - IL-to-internal-model passes (`ILMethodCodePass`, `ILMethodLabelPass`, `ILMethodNextInstructionPass`, `ILMethodBuildEvaluationStackPass`, `ILAddressFromLabelPass`)
  - Optimizer passes (`IL*Optimizer.cs` — increment, field-increment, set-field, object-initializer, branch/compare-against-constant optimizations, etc.) that rewrite the operation list before emit
  - Emit passes (`ILMethodEmitPass`, `ILTypeVTablePass`, `ILTypeStaticFieldInitPass`, `ILStringResourcesPass`, `ILRawAssemblyPass`) that write the final `.asm` text
  - `Operands/` holds the `ILOperation`/opcode-to-asm-macro mapping logic used during emit.
- `C64Lib/` — the stub API (`C64.cs`, `Sprites.cs`, `Sound.cs`, `Joystick.cs`, `Debug.cs`, `C64Address.cs`) that C64 programs reference. `RawAssemblyAttribute` lets a project embed hand-written asm resources directly into the output.
- `Demo/` — a sample C64 program (a port of the game Hunchback, under `Demo/Hunchback/`) written against `C64Lib`, used to exercise the compiler end-to-end. `Program.cs` is the entry point (`Main`) the compiler processes.
- `C64Presentation/` — another C64Lib-based program (a slide-deck app rendered on the C64) with its own `run.bat`.
- `SimpleEmulator/` — a minimal from-scratch 6502 emulator (`Emulator.cs`, `Registers.cs`, `AssemblyInstructions.cs`) used to execute compiled `.prg` files headlessly for unit tests (no VICE dependency for test execution itself, but the `.prg`/`.labels` files are produced via VICE/64tass first).
- `C64TestFramework/` — bridges NUnit tests to the compiler pipeline via PostSharp. `RunInEmulatorAspect` is a `MethodInterceptionAspect` (`[RunInEmulatorAspect]`, applied assembly-wide to `Compiler.Test.*` in `Test/assembly.cs`) that intercepts each `[Test]`/`[TestCase]` method call, loads `prg/unittest.prg` into a `SimpleEmulator.Emulator`, copies method arguments into emulated memory, runs the compiled 6502 routine, and copies the return value/assertion result back — so the *test method body* is actually compiled to 6502 and executed on the emulator, not run as normal C#. `Assert.cs` provides no-op `C64TestFramework.Assert` stand-ins (aliased over `NUnit.Framework.Assert` in test files) whose calls get compiled into the emulator-side assertion protocol (result byte at `0x20`, message pointer at `0x2E`/`0x2F`).
- `Test/` — the NUnit test project (`Compiler.Test`). Each test class under `Test/*.cs` is compiled to `asm/unittest/*.asm` and executed in `SimpleEmulator` via the aspect above. `assembly.cs` wires up the `RunInEmulatorAspect`.
- `asm/` — hand-written 6502 support code:
  - `asm/helper/*.asm` — low-level runtime: stack machine, locals stack, heap/GC (`GC.asm`), arithmetic, branching, object layout, zero-page usage (`zp.asm`).
  - `asm/*.asm` (top level, e.g. `C64.asm`, `c64sprite.asm`, `C64Sound.asm`, `c64Joystick.asm`, `system.asm`, `main.asm`, `unittest.asm`) — C64-specific I/O routines and the top-level program entry points that `.include` the compiler-generated code.
  - `asm/generated/`, `asm/unittest/`, `asm/presentation/` — compiler output (gitignored); regenerated by running the compiler against `Demo`, `Test`, or `C64Presentation` respectively.

## Build & run

Target framework is `net10.0` for the executable/test projects; `C64Lib` and `SimpleEmulator` target `netstandard2.x`.

```
dotnet build                 # builds the whole solution (C64.sln)
```

Building `Compiler.Test` (and `Demo`, `C64Presentation`) has a `PostBuild` MSBuild target that runs that project's `run.bat`, which chains: run `Compiler.exe` against the built `.dll` to (re)generate `.asm` into the matching `asm/<target>` folder, then invoke `64tass` to assemble a `.prg`, then (for `Demo`) launch VICE (`x64sc.exe`). This means **a normal `dotnet build` of `Demo`, `C64Presentation`, or `Compiler.Test` requires `64tass` and, for non-test targets, VICE to be installed at the hardcoded paths in the respective `run.bat`** (e.g. `c:/tools/64tass-1.60.3243/64tass.exe`, `c:\tools\VICE\bin\x64sc.exe`). Building only `Compiler` or `C64Lib` has no such dependency.

Running the full test suite (`Test/Compiler.Test.csproj`) requires PostSharp (`PackageReference PostSharp 2026.0.16`) to weave `RunInEmulatorAspect` into the test assembly at build time, and requires the `Test/run.bat` post-build step (compiles tests to `asm/unittest`, assembles via 64tass into `prg/unittest.prg`) to have completed successfully before the actual `dotnet test` execution, since each test method's real logic only exists once compiled into that `.prg`.

```
dotnet test Test/Compiler.Test.csproj     # run all compiler/codegen tests (via emulator)
```

There is no built-in single-test filter documented here beyond standard `dotnet test --filter`/NUnit `[TestCase]` selection (e.g. `dotnet test --filter "FullyQualifiedName~TestAdd"`), but note the emulator execution depends on labels resolved from `prg/unittest.labels`, which come from compiling the *whole* test assembly — you can't compile/assemble a single test in isolation.

The root `run.bat` and `Demo/run.bat` follow the same compile→assemble→launch-VICE pattern for the `Demo` (Hunchback) program.

## Working on the compiler

- Adding IL opcode support or an optimization means adding a new `ICompilerMethodPass` (or extending an existing `IL*Optimizer`) and wiring it into the pass list in `Compiler/Program.cs::Main` — pass order matters (optimizers run after the evaluation-stack/label passes and before `ILMethodEmitPass`).
- `Operands/OperandBase.cs` and friends define how an `ILOperation` renders itself as an asm macro invocation during `ILMethodEmitPass`.
- Storage sizing/layout logic (used for locals, parameters, and object fields) lives in `TypeExtensions.cs` (`GetStorageBytes()`, `IsReferenceCounted()`) and is consumed via `CompilerMethodContext`/`CompilerContext` helpers in `ICompilerPass.cs`.
- When a compiler change affects codegen, the generated `.asm` under `asm/generated`, `asm/unittest`, `asm/presentation` is expected to be regenerated (it's gitignored) rather than hand-edited.
