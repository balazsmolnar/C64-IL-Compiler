# Catacombs: AAA brief

Shared ground rules for everyone (people and agents) working on bringing
Catacombs up to the level of the best modern C64 releases. Read this
before touching anything.

## The bar

Benchmarks: *Eye of the Beholder* (C64, 2022), *Sam's Journey*, *Lykia*,
*Briley Witch Chronicles*, *Knight 'n' Grail*. A screenshot of any game
state should be mistakable for one of those: dense, deliberate pixel art,
no flat single-colour areas, no programmer-art lines, no colour clash, no
flicker, consistent light and palette.

## Art direction

- Dark gothic catacomb. Screen background ($D021) and border are BLACK,
  always. Light comes from the wall torches: warm (orange/yellow/brown)
  near them, falling off into cold greys/blues and black.
- MultiColor bitmap mode, 160x200 double-wide pixels, per-cell colours
  (video matrix hi/lo nibble + colour RAM) chosen freely per 8x8 cell.
  Shade with dithering, in the classic C64 luminance ramps
  (black -> blue/brown -> dark grey/red -> mid grey/... -> white).
- Rooms differ by a palette theme (cold stone, mossy green, blood/rust,
  violet crypt...) and by props, not by a flat background colour.
- Everything is drawn from the same light direction and with the same
  outline/shading conventions as the rooms.

## Screen layout (fixed, so parallel work doesn't collide)

- Rows 0-20 (y 0..167): the room viewport, full width.
- Rows 21-24 (y 168..199): the status panel (health, treasure, weapon,
  minimap). Nothing but the HUD draws there; the HUD draws nowhere else.

## Gameplay (keep)

One room on screen at a time, fixed north-up perspective view; the player
is a hardware sprite walking freely with W/A/S/D, SPACE crosses a door or
attacks. Monsters guard rooms; treasure and weapons are picked up. These
may be extended (joystick, more content, win/lose flow) but not replaced.

## Technical rules

- Compiler / C64Lib / asm runtime changes are welcome but must be GENERIC
  improvements (useful to any C64Lib program), never Catacombs-specific
  hacks, and must follow the repo's CLAUDE.md: unsupported C# is a coded
  diagnostic, and "pay only for what you use" (Hunchback's segment sizes
  from `Hunchback/measure.bat` must be unchanged by anything it doesn't
  use). Run the affected unit tests.
- Gameplay state lives in C#; hand-written asm belongs in the generic
  runtime (`asm/`), not in the game.
- uint/int are 8-bit and ulong is 16-bit in this compiler. Deep call
  chains overflow the 256-byte locals stack silently: keep frames small.
- Assets are generated by checked-in scripts (Python 3 + Pillow are
  installed) under `Catacombs/art/`, so they can be regenerated and
  iterated on; never hand-paste opaque byte blobs without their source.
- Memory is finite: watch the segment map the build prints.

## Looking at the game

Never synthesize keypresses into VICE. To see a state that needs input to
reach, add a scene: code under `#if SCENE_NAME` that boots the game
straight into that state (see `Program.Main`), then

    & "<root>\tools\catacombs-shot.ps1" -Root "<root>" -Scene NAME -OutPrefix "<root>\.debug-tmp\name" -Shots 3 -IntervalMs 500

builds, runs it in its own VICE instance, and writes cropped screenshots
(`name1.png`, ...) to read with the Read tool. No `-Scene` = the real game
from power-on. Several of these can run at once; never call
`vice-launch.ps1`/`vice-close.ps1` without `-KeepOthers`/`-ProcessId`,
since the plain forms kill every VICE on the machine, including other
agents'. Animation is judged from several shots a few hundred ms apart.
The first frames after launch can contain a stray keypress from VICE's
own autostart typing; that is not a game bug.
